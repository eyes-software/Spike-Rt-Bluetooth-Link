# BluetoothLink

PC 上で動作する Bluetooth データ送受信ツール (C# / WinForms)。

**Bluetooth Classic (RFCOMM/SPP)** と **BLE (GATT)** の両方に対応し、以下の 3 機能を提供します。

1. **ペアリング** — デバイス検索、ペアリング / ペアリング解除
2. **サーバー / クライアント接続と双方向のデータ送受信**
3. **送受信データのファイル書き出し**

## 動作要件

| 項目 | 内容 |
| --- | --- |
| OS | Windows 10 バージョン 2004 (build 19041) 以降 / Windows 11 |
| ランタイム | .NET 10 デスクトップランタイム |
| ハードウェア | Bluetooth アダプター (BLE を使う場合は BLE 対応のもの) |
| ライブラリ | [32feet.NET](https://github.com/inthehand/32feet) `InTheHand.Net.Bluetooth` 4.2.4 / `InTheHand.BluetoothLE` 4.0.44 |

## プリセット

接続先ごとの UUID・区切り・BLE プロファイルの組み合わせをプリセットとして用意しています。プリセットを選ぶと必要な欄が自動で埋まります。

| プリセット | 方式 | サービス / 特性 | 既定の区切り |
| --- | --- | --- | --- |
| Classic: SPIKE Hub / SPP | RFCOMM | `00001101-…` (SPP) | CR 区切り |
| Classic: BluetoothLink 独自 | RFCOMM | `9C6D7B1E-…` | 改行区切り (CRLF) |
| Classic: カスタム | RFCOMM | 任意入力 | 区切りなし |
| **BLE: Pybricks (stdio)**（起動時の既定） | GATT | `c5f50001-…` / `c5f50002-…` (Command/Event) | CR区切り |
| BLE: Nordic UART (NUS) | GATT | `6e400001-…` / `…0002` 書込 / `…0003` 通知 | 改行区切り (CRLF) |
| BLE: カスタム | GATT | 任意入力 | 区切りなし |

プリセットを切り替えると、**UUID だけでなく「区切り」も接続先に合った既定値へ自動で切り替わります**（例: SPIKE Hub なら CR 区切り、Pybricks なら改行区切り）。区切りはそのあと手動で変更できます。

「カスタム」を選んだときだけ UUID 欄を編集できます。`1101` のような 16bit 短縮 UUID も受け付けます。

Classic はサーバー (待ち受け) / クライアント (接続) の両方になれます。**BLE では PC は常にセントラル (クライアント)** なので、ハブ側がペリフェラルとして動いている必要があります。

## 画面と使い方

### 1. デバイス検索 / ペアリング

検索・一覧は、選択中のプリセットの方式 (Classic / BLE) に合わせて切り替わります。

| 操作 | 説明 |
| --- | --- |
| デバイス検索 | **BLE**: アドバタイズを受信し続け、見つかった順に一覧へ追加します（通常 1 秒以内に最初の機器が出ます）。ボタンが「検索停止」に変わり、いつでも止められます。検索中も操作でき、見つかった時点で選んで接続できます。<br>**Classic**: Windows の問い合わせに**約 30 秒**かかります（短縮する手段がありません）。待っている間も一覧が空にならないよう、まずペアリング済みを表示します。 |
| ペアリング済みを表示 | OS に登録済みのデバイスを一覧表示します。 |
| ペアリング | 選択したデバイスとペアリングします。PIN 欄が空なら Windows のペアリング UI に委ねます。固定 PIN の機器 (`0000` / `1234` など) は PIN 欄に入力してください。 |
| ペアリング解除 | 選択したデバイスの登録を削除します。 |

BLE の検索結果には**電波強度 (dBm)** と、アドバタイズに含まれるサービスの目印が出ます。Pybricks のハブは `[Pybricks]`、Nordic UART を持つ機器は `[NUS]` と表示されるので、周囲に多数の BLE 機器があっても見分けられます。

> BLE 機器にはペアリング不要で接続できるものも多くあります (Pybricks のハブなど)。その場合はスキャンで見つけてそのまま接続してください。

### 2. 接続

プリセット、区切り、役割 (Classic のみ) を選んで **接続 / 待ち受け開始** を押します。

> **サーバーとクライアントで UUID と区切り設定を必ず一致させてください。**

#### 区切り (フレーミング)

RFCOMM も BLE の通知も、送信側の 1 回の書き込みが受信側の 1 回の読み取りに対応する保証がありません (BLE は MTU、およそ 20 バイトで分割されます)。用途に応じて選択します。

| モード | 送信時 | 受信時 |
| --- | --- | --- |
| 区切りなし (raw) | そのまま送出 | 届いたチャンクを 1 件として扱う |
| 改行区切り (CRLF) | 末尾に `CRLF` を付加 | `LF` までを 1 件として切り出す (`CR` は除去) |
| CR区切り (0x0D) | 末尾に `CR` を付加 | `CR` までを 1 件として切り出す |
| 長さ付き (4byte BE) | 先頭に 4 バイトのビッグエンディアン長を付加 | 長さ分を 1 件として切り出す |

**CR 区切り**は LEGO SPIKE Hub 向けです。公式ファームのハブは SPP 上で `{"i":…,"m":…,"p":…}` という JSON を **CR (0x0D) のみ**で終端するため、LF を探す「改行区切り」では 1 件も切り出せません。

### 3. データ送受信 / モニタ / ファイル書き出し

- 送信形式は **テキスト** または **16 進 (HEX)**。HEX は `48 65 6C`、`0x48,0x65`、`48-65` のいずれの表記でも解釈します。
- 文字コードは UTF-8 / Shift_JIS / ASCII / UTF-16 LE から選択。送信時のエンコードとログのテキスト表現の両方に使われます。
- `Ctrl+Enter` で送信できます。
- Classic サーバーで複数台が接続している場合、送信は接続中の全セッションへ行われます。

#### 高頻度受信への対応

送受信の処理と画面描画を分離しているため、**受信レートが上がっても UI は固まりません**。

```
[受信/送信スレッド]  ← UI には一切触れない
   ├─ 統計カウンタを Interlocked で加算
   ├─ リングバッファ (既定 200,000 件) へ 1 件積む
   └─ 書き出し待ち行列へ積む
                  │
      [書き出し専用タスク] → まとめ書き + 定期フラッシュ → .log / .bin
                  │
[画面更新タイマー 100ms]
   ├─ 統計を更新 (件数・バイト数・件/秒・バイト/秒)
   └─ 仮想モード ListView を更新 (見えている行だけ描画)
```

要点は次の 3 つです。

- **モニタは仮想モードの ListView**。描画コストは「画面に見えている行数」だけに比例し、受信レートとは無関係です。16 進化や文字列デコードも、表示される行についてのみ実行します。
- **データを間引きません。** リングバッファに直近 200,000 件を保持し、スクロールして遡れます。それ以前のものも**ファイルには全件残ります**。統計は 1 件も取りこぼさずに数えます。
- **取りこぼしは必ず可視化します。** 万一ディスクが追いつかず書き出し待ち行列が溢れた場合、統計欄に `★記録欠落 N 件` と**赤字**で表示し、ログファイル末尾にも件数を記録します。

実測値 (Release ビルド):

| 条件 | UI 応答時間（平均 / 最大） | 記録欠落 |
| --- | --- | --- |
| 2,000 件/秒 × 5 秒（BLE の現実的な上限付近） | 4.9 ms / 42 ms | なし |
| 10,000 件/秒 × 10 秒（余裕の確認） | 4.7 ms / 37 ms | なし |
| 全力投入 約 100 万件/秒 × 3 秒（参考） | 50〜120 ms / 300〜700 ms | 書き出しが追いつかない分を欠落件数として表示 |

> 十万件/秒級の極端なレートでは CPU が飽和し、UI の応答が数百 ms 遅れることがあります。BLE の現実的なレートでは問題ありません。

「自動スクロール」を外すとモニタの位置が固定され、受信を続けながら過去のデータを読めます。

#### 出力ファイル

接続 (または待ち受け) を開始した時点で `logs/` フォルダーに以下が作成されます。

```
logs/
  bt_20260913_101530_MyDevice.log      … テキストログ (タブ区切り, UTF-8 BOM 付き)
  bt_20260913_101530_MyDevice_tx.bin   … 送信した生バイト列
  bt_20260913_101530_MyDevice_rx.bin   … 受信した生バイト列
```

テキストログの各行は次の 5 列です。Excel やスクリプトでそのまま読めます。

```
時刻                       方向  バイト数  16進                    テキスト
2026-09-13 10:15:32.104    TX    4         50 49 4E 47             PING
2026-09-13 10:15:32.310    RX    4         50 4F 4E 47             PONG
```

`INF` / `ERR` 行には接続・切断・エラーの記録が入ります。`.bin` は「生データ(.bin)も書き出す」のチェックで切り替えられます (区切りのバイトや BLE のコマンド/イベントバイトは含まれず、ペイロードのみが連結されます)。

画面のログ表示は 2000 行を超えると古い行を捨てますが、**ファイルには全件残ります**。

## 接続先別のメモ

### LEGO SPIKE Hub (公式ファーム)

プリセット **Classic: SPIKE Hub / SPP** + **クライアント**。ハブ側が SPP サーバーなので、こちらは必ずクライアントです。COM ポート経由ではなく RFCOMM を直接掴みます。

- LEGO SPIKE アプリなど他アプリがハブを掴んでいると接続に失敗します。
- 送受信されるのは JSON で、終端は CR です。

### Pybricks ファームのハブ

プリセット **BLE: Pybricks (stdio)**。Pybricks は Bluetooth Classic を持たず **BLE 専用**です。

**stdin / stdout が流れるのは、ハブ上でユーザープログラムが実行中のときだけです。** 接続しただけでは何も起きません。接続後に **プログラム開始** ボタン(または **REPL開始**)を押してください。

| ボタン | 送るコマンド | 用途 |
| --- | --- | --- |
| プログラム開始 | `START_USER_PROGRAM` (0x01) | ハブに保存済みのプログラムを実行する |
| 停止 | `STOP_USER_PROGRAM` (0x00) | 実行中のプログラムを止める |
| REPL開始 | `START_REPL` (0x02) | 対話シェルを起動する。プログラムなしで送受信を試せる |

接続すると、ハブから届く**ステータスレポート**をログに出し、画面右に「プログラム: 実行中 / 停止中」を表示します。これが更新されていれば通信路は生きています。

#### プロトコルバージョンによる経路の違い

接続時に Software Revision 特性からプロトコルバージョンを読み、stdio の経路を自動で切り替えます。

| プロトコル | 送信 (stdin) | 受信 (stdout) |
| --- | --- | --- |
| v1.3.0 以降 | Command/Event 特性に `WRITE_STDIN` (0x06) を付けて書き込み | `WRITE_STDOUT` (0x01) イベント |
| v1.3.0 未満 | **Nordic UART Service の RX 特性**へそのまま書き込み | **NUS の TX 特性**の通知 |

新しいファームでも NUS が残っていることがあるため、受信は Command/Event と NUS TX の**両方**を購読します。接続時のログにどちらの経路を使っているかが出ます。

#### その他

- Pybricks Code (ブラウザ) が同じハブに接続していると接続できません。先に切断してください。
- Pybricks 側のプログラムでは `sys.stdin` / `print()` を使います。
- 1 回の書き込みサイズは Hub Capabilities 特性から取得した値を使います (取得できなければ MTU から算出)。

### SPIKE-RT / RasPike など独自ファーム

USB 仮想 COM / Bluetooth でのシリアル通信は提供されていますが、プロトコル (終端・形式) は書き込んだアプリケーション次第です。**Classic: カスタム** で UUID と区切りを合わせてください。RasPike 構成では PC の通信相手が Raspberry Pi (Wi-Fi/SSH) になり、Bluetooth を使わない場合があります。

## PC 2 台でのテスト手順

1. 2 台をあらかじめ Windows の設定でペアリングしておく (または本ツールのペアリング機能を使う)。
2. 片方で **Classic: BluetoothLink 独自** を選び、サーバーにして **待ち受け開始**。
3. もう片方で相手を一覧から選択し、同じプリセット + クライアントで **接続**。
4. 双方の送信欄から文字列を送り合い、ログと `logs/` のファイルを確認する。

## トラブルシューティング

| 症状 | 対処 |
| --- | --- |
| 「Bluetooth アダプターが見つかりません」 | アダプターの接続と、Windows の Bluetooth が ON になっているかを確認。 |
| 待ち受け開始で失敗する | 同じ UUID で別のアプリが待ち受けている可能性があります。UUID を変えて試してください。 |
| 接続がタイムアウトする | 相手側が同じ UUID で待ち受けているか、ペアリング済みか、電波が届いているかを確認。BLE では相手側でプログラムが動いているかも確認。 |
| BLE で「サービスが見つかりません」 | ファームウェアと UUID の組み合わせを確認。Pybricks 以外のファームでは Pybricks サービスは存在しません。 |
| 受信しても 1 件も表示されない | 「区切り」が相手の終端文字と合っていない可能性があります。終端文字が現れないと、データは組み立てバッファに溜まったまま 1 件も切り出されません。SPIKE Hub なら CR 区切り、迷う場合は一度「区切りなし」で生データを確認してください。 |
| 最後の 1 行だけ出てこない | 終端文字のない出力が残っている状態です。切断するか、Pybricks ならプログラムの停止を検知した時点で吐き出します。それでも出ない場合はアプリを強制終了していないか確認してください (正常に閉じればファイルへ出し切ります)。 |
| Pybricks に接続できたが無反応 | ユーザープログラムが動いていない可能性が高いです。**プログラム開始** か **REPL開始** を押してください。ログのステータスレポートで実行状態を確認できます。 |
| 「通知を有効にできませんでした」 | 他のアプリ (Pybricks Code など) がハブを掴んでいます。そちらを切断してから再試行してください。 |
| 文字化けする | 送受信双方の文字コード設定を合わせてください。 |
| 統計欄に赤字で「記録欠落」が出る | 待ち行列のあふれか、ディスクへの書き出し失敗です。内訳が括弧内に出ます。前者は出力先を高速なドライブに変えるか「生データ(.bin)も書き出す」を外す、後者はモニタに出る原因 (空き容量・アクセス権など) を確認してください。 |
| 送信が途中で失敗した | BLE は MTU 単位で分割送信するため、一部だけ相手に届くことがあります。実際に送出できた分は送信として記録し、モニタには「N バイト送出後に中断」と出ます。 |
| 「モニタ表示外 N 件」と出る | 画面に保持する 200,000 件を超えました。**ファイルには全件残っています**ので、ログフォルダを開いて確認してください。 |
